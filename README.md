# Музейные выставки — REST API (Lab 1 RBPO, Задание 3)

## Назначение

Приложение — backend для музея: оно ведёт учёт экспонатов, выставочных залов и
выставок, позволяет кураторам планировать размещение экспонатов по залам,
открывать и закрывать выставки, отправлять экспонаты на реставрацию.

Данные хранятся в PostgreSQL, доступ к API — по HTTP Basic с ролями `ADMIN` и `CURATOR`.
Приложение не имеет UI: с ним работают через REST-запросы (Postman-коллекция в комплекте).

## Предметная модель

```
app_user (пользователь) 1 ──< exhibition (выставка) 1 ──< exhibit_placement (размещение)
                                                              │        │
                                              exhibit (экспонат) ┘        └ exhibition_hall (зал)
```

| Сущность | Что описывает | Ключевые поля и связи |
|---|---|---|
| **Пользователь** (`app_user`) | Сотрудник музея | `username`, `name`, `role` (`ADMIN`/`CURATOR`), BCrypt-хэш пароля |
| **Зал** (`exhibition_hall`) | Помещение, где выставляются экспонаты | `name`, `area` (м²), `isAvailable` — открыт ли зал для размещения |
| **Экспонат** (`exhibit`) | Предмет коллекции | `inventoryNumber` (уникальный), `name`, `condition`, `requiredArea` (сколько м² занимает) |
| **Выставка** (`exhibition`) | Мероприятие с датами и куратором | `name`, `startDate`, `endDate`, `status`, ссылка на куратора |
| **Размещение** (`exhibit_placement`) | Факт нахождения экспоната на выставке в зале | ссылки на экспонат, выставку и зал, `status`, `placedAt`, `removedAt` |

Состояния:

- экспонат: `EXCELLENT`, `GOOD`, `DAMAGED`, `RESTORATION`, `LOST`;
- выставка: `PLANNED → ACTIVE → COMPLETED` (или `PLANNED → CANCELLED`);
- размещение: `PLANNED` (запланировано), `INSTALLED` (установлено), `REMOVED` (демонтировано).

Один экспонат может быть размещён на конкретной выставке только один раз
(`UNIQUE(exhibit_id, exhibition_id)`); на двух активных выставках одновременно — нельзя
(проверяется бизнес-операцией).

## Возможности

### CRUD (базовое управление данными)

| Ресурс | Путь | Кто может изменять |
|---|---|---|
| Пользователи | `/api/users` | только `ADMIN` |
| Залы | `/api/halls` | создание/изменение/удаление — `ADMIN`; чтение — все авторизованные |
| Экспонаты | `/api/exhibits` | `ADMIN`, `CURATOR` |
| Выставки | `/api/exhibitions` | `ADMIN`, `CURATOR` |
| Размещения | `/api/exhibit-placements` | `ADMIN`, `CURATOR` |

Для каждой сущности доступны `GET` (список и по id), `POST`, `PATCH`, `DELETE`.

### Бизнес-операции (5)

CRUD меняет одну запись, бизнес-операции — состояние нескольких связанных сущностей
и проверяют бизнес-правила. Все выполняются в транзакции; при нарушении правил
возвращается `409 Conflict` с объяснением.

| № | Операция | Эндпоинт | Правила |
|---|---|---|---|
| 1 | Разместить экспонат на выставке | `POST /api/business/placements` | выставка `PLANNED`/`ACTIVE`; экспонат не `RESTORATION`/`LOST`; зал открыт; хватает свободной площади; экспонат не занят на другой активной выставке |
| 2 | Переместить экспонат в другой зал | `POST /api/business/placements/{id}/move` | размещение не снято; выставка не завершена; новый зал открыт и вмещает экспонат |
| 3 | Открыть выставку | `POST /api/business/exhibitions/{id}/open` | только `PLANNED`; дата начала наступила; есть экспонаты; все залы доступны; размещения → `INSTALLED` |
| 4 | Закрыть выставку | `POST /api/business/exhibitions/{id}/close` | только `ACTIVE`; все размещения → `REMOVED`, выставка → `COMPLETED`, площадь залов освобождается |
| 5 | Отправить экспонат на реставрацию | `POST /api/business/exhibits/{id}/restoration` | нельзя при активной выставке, при `LOST` и повторно; из запланированных выставок экспонат снимается |

Ограничения целостности продублированы на уровне БД: `CHECK` на статусы и площади,
`UNIQUE` на инвентарный номер, имя зала и пару «экспонат + выставка», внешние ключи
с `ON DELETE RESTRICT`, согласованность `status`/`removed_at`.

## Запуск

Требования: JDK 17+, PostgreSQL 13+, Maven.

1. Создать БД и роли (один раз, от суперпользователя `postgres`):

```bash
psql -U postgres -h 127.0.0.1 \
  -v owner_password='пароль_владельца_схемы' \
  -v app_password='пароль_приложения' \
  -f db/init.sql
```

Пароли не хранятся в репозитории: скрипт принимает их параметрами и создаёт роли,
только если их ещё нет (повторный запуск безопасен). Эти же значения нужно указать
в `.env` (`DB_INIT_PASSWORD` и `DB_PASSWORD`).

Скрипт создаёт базу `museum` и двух пользователей:

- `museum_owner` — владелец схемы, выполняет `schema.sql`/`data.sql`;
- `museum_app` — пользователь приложения: только `SELECT/INSERT/UPDATE/DELETE`,
  без права создавать таблицы.

2. Создать `.env` в корне проекта (файл в `.gitignore`, шаблон — `.env.example`):

```properties
DB_URL=jdbc:postgresql://127.0.0.1:5432/museum
DB_USERNAME=museum_app
DB_PASSWORD=...
DB_INIT_USERNAME=museum_owner
DB_INIT_PASSWORD=...
```

3. Запустить приложение:

```bash
./mvnw spring-boot:run
```

При старте `schema.sql` создаёт таблицы, `data.sql` загружает тестовые данные
(идемпотентно), Hibernate проверяет соответствие схемы сущностям.

### Тестовые учётные записи

| Логин | Пароль | Роль |
|---|---|---|
| `admin` | `admin123` | ADMIN |
| `curator` | `curator123` | CURATOR |

Тестовые данные: 3 зала (один закрыт), 5 экспонатов, 3 выставки в разных статусах,
4 размещения — есть что проверить сразу после запуска.

## Коллекция запросов Postman

Файлы:

- `postman/collections/lab1RBPO.postman_collection.json`;
- `postman/environments/lab1RBPO.postman_environment.json`.

Как запустить:

1. Импортировать оба файла в Postman (`Import`).
2. Выбрать окружение **Lab1 RBPO — local**.
3. Выполнить коллекцию целиком через **Run collection** (порядок папок важен)
   или открыть нужную папку вручную.

Структура коллекции:

| Папка | Содержимое |
|---|---|
| 1. Сценарий | 13 запросов: создание залов, экспоната и выставки → размещение → перемещение → открытие → негативная проверка → закрытие → реставрация |
| 2. CRUD: пользователи | список, по id, создание, изменение, удаление |
| 3. CRUD: залы | список, по id, создание, изменение, удаление |
| 4. CRUD: экспонаты | список, по id, создание, изменение, удаление |
| 5. CRUD: выставки | список, по id, создание, изменение, удаление |
| 6. CRUD: размещения | подготовка данных + полный CRUD размещения |
| 7. Очистка сценария | необязательное удаление данных, созданных сценарием |

Сценарий использует переменные и сам сохраняет id созданных объектов, поэтому
повторные запуски не конфликтуют: имена содержат уникальный `runId`, даты
выставки вычисляются относительно текущего момента. Коллекция содержит 65
проверок (`pm.test`), которые валидируют и коды ответов, и изменение состояния
(`PLANNED → ACTIVE → COMPLETED`, `GOOD → RESTORATION` и т.п.).

Проверка из консоли (если установлен Newman):

```bash
newman run postman/collections/lab1RBPO.postman_collection.json \
  -e postman/environments/lab1RBPO.postman_environment.json
```

## Аутентификация и ошибки

- HTTP Basic; пользователи хранятся в БД, пароли — BCrypt.
- `ADMIN` управляет пользователями и залами, `CURATOR` — выставками, экспонатами,
  размещениями и бизнес-операциями.
- Публичные эндпоинты: `GET /api/hello`, `GET /api/status`.
- Ошибки: `400` — невалидное тело, `401` — нет аутентификации, `403` — нет прав,
  `404` — объект не найден, `409` — нарушено бизнес-правило или ограничение БД.
